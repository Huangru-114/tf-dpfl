# exp001 — 正交化的 L2 接线验证

> ⚠️ **这些数字不是真 smoke 结果。** 本次运行在**合成数据**上跑，因为本会话所在容器的
> 出网代理封了 `cs.toronto.edu`（403），CIFAR-10 下不下来。
> 合成数据：50000/10000 张 32×32×3，标签均衡取 0–9，像素均值随标签线性变化
> （`x ~ N(12+23y, 18)`），所以模型学得动、Dirichlet 分区不会产出空客户端。
>
> **准确率 / ASR 的绝对值一律无意义，不要引用。** 本次运行只回答一个问题：
> 「三条轴有没有真的挂进联邦循环、跑完 5 轮不崩」——CLAUDE.md 里 L2 的定义正是
> 「验证接线而不是算法」。真实数据的 smoke 仍需在集群上重跑一次。

环境：TF 2.15.1 / Keras 2.15（容器内临时装的，仓库 requirements 只写了 `tensorflow>=2.12`）。

## 跑了什么

```bash
# 对照组：vanilla 策略，走 MalMixin is None 分支 —— 「没跑坏」的基准
python main.py --config ../experiments/smoke-base.yaml \
    --framework hier_pfedme --attack_method badnet --defense none

# 关键格：改动前这一格里恶意客户端会跑成朴素 FedAvg
python main.py --config ../experiments/smoke-base.yaml \
    --framework hier_pfedme --attack_method neurotoxin --defense none
```

## 结论 1：陷阱 #1 的行为级证据

`neurotoxin × hierpfedme` 的日志：

```
[Setup] client classes | benign=PFedMeClient | malicious=NeurotoxinPFedMeClient
  [Client  0] Starting Hier-pFedMe | λ=15.0, plr=0.00992, K=5, epochs=1, batches/epoch=131
  [Client  0] Round 1 | Hier-pFedMe(λ2=15.0, K=5) | loss=1.6438
  [Client  0] Round 1 | Neurotoxin(mask=top-5%, ref=edge_weights)
```

改动前这里是 `malicious=NeurotoxinClient`（一个 `FedAvgClient` 子类），恶意客户端
**根本不会打印 Hier-pFedMe 那两行** —— 它跑的是朴素 FedAvg。
现在恶意客户端跑完整的 pFedMe（内层 K=5 + Moreau 步），再在**上传物**上叠掩码。

## 结论 2：badnet × hierpfedme 没跑坏

5 轮跑完，`EXIT=0`。GM 准确率逐轮上升 0.0966 → 0.1702 → 0.2049 → 0.3533 → …，
PM 加权 C-Acc = 0.8136。恶意客户端自己的模型被后门污染
（`local_malicious_asr` 多轮为 1.0），良性客户端的 `local_benign_asr` ≈ 0.06–0.10，
5 轮内没有扩散 —— 这对 badnet 在这个规模下是预期的，且**不是本次改动要解决的问题**。

## 结论 3：12 个「攻击 mixin × PFL 方法」组合都能连跑两轮

用小模型在本地逐个构造并跑两轮（含 peer 权重逐轮变化，验证 CerP 的 retrace 防护）：

| | FedAvg | pFedMe | Ditto | FedRep |
|---|---|---|---|---|
| Neurotoxin | ✅ | ✅ | ✅ | ✅ |
| CerP | ✅ | ✅ | ✅ | ✅ |
| Bad-PFL | ✅ | ✅ | ✅ | ✅ |

「upload ≠ 个性化模型」在 pFedMe / Ditto / FedRep 下都成立；FedAvg 下两者本来就相同
（无个性化模型），符合预期。

## 顺带发现并修掉的一个 bug（严重）

`main.load_config` 旧实现**先 `open(path)` 再 `parse_known_args()`**，解析出的
`args.config` 全仓库从未被使用 → **`--config` 被静默忽略**。

后果：`run_smoke.sh` 传的 `--config ../experiments/smoke-base.yaml` 一直无效，
所谓的「3 分钟 smoke（10 client / 5 round / cifar10）」每次实际跑的都是
`fedavg/config/config.yaml`（**cifar100 / 100 client / 40 round**），日志里没有任何异常。
**整个 L2 验收层此前等于不存在。**

不修它本会话的 L2 就跑不了，所以一并修了。守卫：`tests/test_config_cli.py`
（AST 断言 `args.config` 被使用、且 `open()` 在 `parse_known_args()` 之后）。

> 这条也意味着：**此前所有标称「smoke」的历史结果都要重新解释**——它们跑的是全量配置。

## harness/collect_metrics.py 的四个缺口（已修）

第一次收集时我误以为「解析器整个没匹配上」，其实 neurotoxin 那份是好的
（`n_malicious_participations = 5`）；badnet 那份读 0 是因为 vanilla 策略。
但这一比暴露了四个真缺口，都已修，并补了 `tests/test_collect_metrics.py`（21 条，纯 Python）：

1. **`acc` 一个都没采集。** CLAUDE.md 要求 metrics.json 含
   `{asr, acc, admitted_count, malicious_selected_rounds}`，而
   `[Cloud] GM=/EM=/PM=` 行被整个丢弃 → 「acc 不低于 baseline N 点」这类判据读不出来。
   现在有 `acc_rounds[]` + `final_acc`（含最终 PM 加权 C-Acc）。
   轮号取自 `[Round N]` 头而不是「第 k 条 Cloud 行 = 第 k 轮」——
   后者在中途崩掉时会整条曲线错位，而错位的曲线看起来完全正常。

2. **vanilla 策略下 `n_malicious_participations` 恒为 0。**
   旧正则只认 `Neurotoxin|Bad-PFL|CerP` 的打印行，而 badnet/blended/dba 的恶意客户端
   跑的是普通方法的 `local_train`，打印的是 `Hier-pFedMe(...)`，没有任何标记。
   0 同时也是「攻击根本没被选中」的取值，两者不可区分。
   现在按 **client_id** 统计（从 `[Backdoor] resolved malicious clients` 解析），
   对所有策略都成立，并给出 `malicious_participation_by_client` 供核对 fix-frequency 的 Q。

3. **`admitted_count` 5 个防御里只有 1 个读得出来。**
   各防御各打各的：flame「admitted 7/10」、multi_krum「selected N clients」、
   dnc「keep N clients」、trimmed_mean/median 干脆不打。解析器只认 flame 那句 →
   defense 轴 4/5 是瞎的。
   修法不是写 5 个脆弱正则，而是在 `RobustAggregationMixin.robust_mean`
   这个**唯一收口处**发一条统一判决行：
   `[Decision] edge0 | flame | admitted 7/10 | rejected=[3, 5]`，
   坐标类防御发 `coordinate-wise | n=10`（`admitted` 记 `None` 而不是 0 ——
   0 会被读成「全部剔除」）。新增防御自动被覆盖。
   守卫：`test_cloud_aggregate_default.py::test_every_defense_emits_the_uniform_decision_line`
   （5 个防御逐个断言）。老日志的 flame 专属行仍能回退解析。

4. **metrics.json 不自描述。** 刚发现 `--config` 会静默失效之后，一份不写明
   「跑的是哪个 config / method / attack / defense / 几轮 / 谁是恶意」的 json
   事后无法判读。现在有 `run` 段。

另新增 `client_failures[]`：`_collect_updates_parallel` 会 catch 掉客户端异常、
把它踢出聚合，run 照常跑完。若恰好是恶意客户端每轮抛异常，ASR 必然是 0 而日志之外
没有任何线索 —— 这是「ASR=0」最常见的真实原因之一，必须显式回传。

带防御的真实 run 验证（`--defense flame --override federation.n_rounds=1`）：
```
    [Decision] edge0 | flame | admitted 1/5 | rejected=[9, 1, 0, 3]
    [Decision] edge1 | flame | admitted 1/5 | rejected=[6, 5, 4, 7]
```
→ 解析出 `admitted_count_mean=1.0`、`rejected_ids=[0,1,3,4,5,6,7,9]`。
（FLAME 只接纳 1/5 是**陷阱 #3**，与本次改动无关。）
